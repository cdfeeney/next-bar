## Why this delta exists

The base PRD predates Stories, Feed, the global composer, named Groups, manual presence pins and
the Account recap archive. Those surfaces have been designed, founder-approved, and in three cases
already built — against no repository requirement text at all. This delta gives them stable,
testable requirement IDs so the traceability chain

`approved decision → PRD requirement → goal acceptance criterion → implementation path → candidate-bound evidence`

can be validated mechanically rather than argued.

Requirement rows, with every field the traceability contract demands, live in
`docs/V8-TRACEABILITY-LEDGER.json`. This file names what changed and why.

## 5. Explicit exclusions

Stated so a reviewer can distinguish "not built" from "deliberately not built".

- **Third-party authentication** (Apple, Google, phone) — `D-C-03`. Two operational-state cards
  depend on it (`Sign-in provider unavailable`, `Verification pending`) and are excluded with it.
- **Gender field** in onboarding — `D-C-04`.
- **Group chat / messaging** — base PRD P1. A **named group** is a different object and is not
  excluded by this; see `D-O-04`.
- **Public audience** — no approved canvas contains one. Pending `D-O-02`.
- **Public like counts and follower metrics** on Feed and Stories — `social-v2-core`,
  `story-tag-placement`, `camera-modes` all state this independently.
- **Hide / "never show me this again"** and any rating control on Next Bar? — base PRD P1.
- **Automatic location for presence** — pins are manual and bar-level; `option-b-manual-pin` states
  "You choose the bar. Next Bar never tracks you automatically."

## 6. Blocked requirements

Not deferred, not missing — specified and approved, but unimplementable without a capability that
does not exist. Both are confirmed by both reviewer families on candidate `e0d25ec1`.

| ID | Blocker |
|---|---|
| `V8-R-STO-014` | Server-side re-encode is absent. Uploads go client → Storage directly, so EXIF/GPS stripping is client-side best-effort and bypassable by a modified client — on a surface that promises venue-tagged, never geotagged. |
| `V8-R-STO-015` | Signed-URL lifetime is not server-enforced. `signedUrlTtlSeconds` is a client-side clamp, so an authorized modified client can mint a shareable bearer URL that outlives both expiry and the friend gate. |

Both close only by routing bytes through a server handler that re-encodes (`sharp` is already a
dependency) and mints URLs server-side — the media-ingestion boundary lane. `OA-01`/`OA-02` supply
the evidence path; they do not supply the capability.

## 7. Requirements whose evidence is owed, not whose behavior is open

Recorded so approval is not mistaken for verification. Three live suites have **never executed** —
never passed, never failed, never forced green: `storiesRls.live.test.ts`,
`friendScoreRls.live.test.ts`, `nightOutsRls.live.test.ts`. Every `RLS`/authorization claim on the
Stories requirements is therefore **asserted, not proven**. `OA-01`/`OA-02` now permit that
evidence to be taken against staging.

## 8. Change control

Approval freezes, together and by digest: this delta, `docs/V8-DECISIONS-2026-08-23.md`,
`docs/V8-TRACEABILITY-LEDGER.json`, and the 16 approved artifact digests recorded in the ledger.

After approval, every goal must pin the release ID, the PRD delta version and digest, its
requirement IDs, exact scope, exclusions, verification and candidate evidence. A later PRD or design
change makes affected goals **stale** until an attended reconciliation explicitly preserves or
replaces their scope. A `complete` goal remains historical evidence; it does not automatically
satisfy a changed requirement.
