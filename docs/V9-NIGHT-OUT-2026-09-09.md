# V9 Night Out goal — what landed, what is pending (V9-02/03/04/05)

Goal g-72a23a7f, run nb-v9-overnight-20260908, on foundation C (`aa9d432`). Four requirement IDs share the planner
and creation code; they were done as sequential slices in this order, and this file says plainly which acceptance
criteria are met in the browser, which are pending, and what still needs the physical iPhone.

## V9-03 — created plan discoverable again (DONE in browser)

Cause (from the foundation-B audit): `get_my_night_outs` excludes plans the caller owns
(`supabase/migrations/0059_night_outs_respond_revision.sql:296`) and no surface listed owned plans
(`StartNightOutButton.tsx:38-41`). Fix: `src/app/friends/_components/YourPlanTonight.tsx`, mounted in `PlansSection`
above the invitations. When the Start button creates a plan it now also records it as tonight's *owned* plan
(`src/lib/ownedNightOut.ts`, localStorage keyed by account + night, other nights pruned on write) — deliberately a
second record, because the existing parked record is a create-recovery guard that the plan page spends on open
(`page.tsx` `forgetStartedNightOut`) and so cannot serve as a way back. The card reads the owned record and fetches the
plan through `get_night_out` — RLS decides what the owner may see, the client invents nothing. States: nothing recorded
→ renders nothing; read failed → says so with Retry (never "no plans"); plan gone/cancelled → forgets it, renders
nothing. The rendered state is scoped to one account and reset synchronously — during the render in which the account
changes, before anything is committed — and every async read is stamped so a late result is dropped; an in-place
account switch therefore never shows the previous account's plan or its bearer link, not even for one frame
(round-1 and round-2 panels, Codex HIGH). Account deletion drops the record with the rest of the account's local
data, working on the raw stored value so a malformed record is erased whole rather than surviving the sweep
(`destroyAccountDataOnDeletion`; round-1 and round-2 panels, both lanes). Returning from another tab and reloading both recover the same plan (the
e2e "V9-03: the plan an owner just created is listed under Plans after returning" asserts the card, its href, and
survival across reload, with `get_my_night_outs` still fixtured as the server answers: `[]`).

Not changed: the server function. Including owned plans in `get_my_night_outs` would be a migration (T0-adjacent,
never applied in an unattended run) and `nightOutsRls.live.test.ts:909` pins the current exclusion; the client surface
is the honest V9 fix and the durable server change is a follow-up decision. "Reopening the app" on a different device
is NOT covered by a localStorage record — stated as the limit.

## V9-04 — searchable people and group selection (DONE in browser)

`src/app/friends/consensus/RecipientPicker.tsx` replaces the chip wall: a "Search people" field (substring on name or
handle), at most eight suggested people with "Show all (N)", a Groups row from `fetchMyGroups` whose members
(`fetchGroupMembers`) join the selection and leave it together unless also picked directly, and a "Selected · N people"
summary with a "Remove <name>" control per person. Loading, failed (with retry) and empty-circle states are distinct.
`mergeSelection` (`src/lib/inviteeSelection.ts`) dedupes direct + group picks; `deriveInviteeIds` is unchanged, so the
submitted set is exactly the visible one.

**Authorization stays on the server (round-1 panel, Codex HIGH).** The inherited `invite_to_night_out` (0050) has no
`is_blocked_between` check — a recorded gap (HFX-R-103) — so a client-cached group roster pushed through it could reach
someone the caller has blocked or who is no longer a member. Every invitation now goes through
`invite_one_to_night_out` (0067): it refuses blocked pairs, and for a person picked *through a group* the page passes
that group id (`inviteeGroupByUser`) so the server re-checks current membership per person. The client roster is a
suggestion, never an authorization. While a create is in flight the picker is frozen (`onBusyChange`), so the visible
selection cannot drift from the snapshot being submitted.

**Default selection — a decision, recorded.** The default remains *everyone you follow*, but it is now explicit: the
summary states it and every person can be removed before submission. An empty default was implemented first and
reverted the same hour: it emptied Group Favorites on arrival (UX-B's approved view of the selected circle) and hid
the deadline row (NO-005 shows it only once someone is selected). The queue's words are "do not *silently* invite
everyone because of an implicit default" — the default is no longer silent or implicit. Pinned by two e2e cases: the
stated default is exactly who gets invited, and removing everyone invites nobody.

## V9-02 — form overflow on iPhone (NOT reproduced in browser emulation; device step pending)

A geometry regression was written first ("V9-02: the plan form never exceeds the viewport width, with long content and
the deadline picker open"): long Area text, the deadline picker open, then `documentElement.scrollWidth`,
`body.scrollWidth` and every field's right edge must stay inside the viewport, and the primary action must be in the
viewport. **It passes on this base on both Playwright devices** (iPhone 13 / WebKit and Pixel 7 / Chromium), so the
overflow the owner sees is not produced by the form's CSS layout under emulation. What emulation cannot exercise and
the phone does: the native `datetime-local` picker chrome in WKWebView, the on-screen keyboard, and the recipient
picker with a real (larger) circle. No CSS was changed blind; the regression stays in the gate so a future layout
change that does overflow turns red, and the physical-iPhone reproduction (with the exact build, origin and iOS version
recorded) is the attended step that decides the fix.

## V9-05 — flow order, organizer shortlist, real invitations with retry (DONE in browser, follow-up run 2026-09-10)

Goal `g-9bc5b136` (run nb-v9-followup-20260909). What changed, and where:

- **Order.** `/friends/consensus` now reads *Plan details* (When / Area / Voting closes) → *Who's going* (the V9-04
  picker) → *Suggested bars* (vibe poll, the organizer's shortlist, Group Favorites, People's Choice) → ONE primary
  action at the bottom. `StartNightOutButton` still owns the whole create → invite → suggest sequence; it renders the
  detail rows first and the button last and takes the page's sections as `children`, so the single component that
  knows the sequence also decides where its button sits. Signed out it renders only the children.
- **The action says what it does.** "Create the Night Out & invite N" (N = accounts in the visible selection), or
  "Create the Night Out" when nobody is selected. The generic `/join` "Invite friends" share is gone from the planner:
  it was never a plan invitation. The plan's own invite link is on the plan page ("Copy invite link"), which the action
  opens.
- **Organizer shortlist.** Up to three bars (the server's own cap, `suggest_night_out_bar` 0044:648), picked from the
  Group Favorites cards ("Add to shortlist") or by name from the catalog ("Add a bar to the shortlist") — the latter
  because a real circle's Group Favorites is empty until scores cross the friend boundary. Snapshotted at the tap like
  the guest list, and put on the board with `suggestAll` (`src/lib/nightOutStart.ts`) right after the invitations; the
  owner is an accepted member from `create_night_out`, so the RPC accepts them. The board on `/night-out/[token]` is
  unchanged and keeps member suggestions and votes.
- **Partial failure.** A refused invite or shortlist bar holds the screen (`startOutcome` gained `failedSuggestions`),
  says exactly what did not send ("1 invite and 1 shortlist bar didn't send"), and "Retry what didn't send" re-runs
  ONLY the failed ids — invites with the group each was picked through, bars through the idempotent suggest RPC —
  then opens the plan once nothing is left unsent. The plan is never re-created; the create button stays disabled.
- **Pinned by** `e2e/night-out.spec.ts` "V9-05: details → people → bars → one action; the shortlist is suggested and
  only the failed invite is retried" (order measured by bounding boxes; one create, one suggestion, two invite calls
  for the refused person; the plan opens only after the retry) and `src/lib/nightOutStart.test.ts` (`suggestAll`,
  `startOutcome`). The existing V9-03/V9-04 journeys were re-pointed at the new button label.

Not done: member voting from the planning flow (votes belong to the plan's board, after creation, by design); the
physical-iPhone check of the reordered form with the keyboard up (attended).

## Swallowed first tap on the Social sub-tabs — found under the loaded gate, fixed product-side

A tap on the Social sub-tabs that landed before React attached its handlers was silently swallowed (Tonight stayed
selected) — for tests and for real users on a slow phone alike. The tabs are now `disabled` until the page has mounted
(`src/app/friends/page.tsx`, the same pattern `VibeQuiz` uses), so a first tap is never lost and Playwright's
enabled-wait is a true hydration signal; the e2e helper taps once after that wait. Earlier attempts to paper over it
in the test (click-until-selected, a server-rendered "marker") were rightly rejected by the panel.
