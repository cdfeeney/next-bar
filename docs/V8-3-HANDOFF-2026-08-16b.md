### Added in the round-2 fix cycle: `suggest_night_out_bar`, deliberately NOT fixed here

An earlier commit in this goal shipped `0051_night_outs_suggest_recheck_before_cap.sql`,
which applied 0050's recheck-before-cap fix to `suggest_night_out_bar`. **It has been
removed.** The goal body authorizes exactly five findings and says the invite race needs
"a new `0050`, `create or replace` only"; `suggest_night_out_bar` is named by none of
them, so 0051 expanded a T0 migration surface past its mandate — which is what the
round-2 panel filed (Codex, medium).

The underlying observation is still believed correct and is carried here rather than
lost: `suggest_night_out_bar` runs its "an idempotent re-suggest never spends the cap"
check **before** the advisory lock, so at the 3-per-member boundary a concurrent
duplicate suggestion for a bar that is already on the board returns `false` instead of
`true`. Same shape as 0048 and 0050, one function over. It was never applied to any
database, so nothing is drifted; it needs its own goal, with its own tier decision and
its own migration number above the live maximum.

### Also carried out of the round-2 fix cycle: simultaneous double-create

Two tabs open on the same account, both tapping Start within the same instant —
before either has parked anything — can still create two plans for the same
night. The cross-tab `storage` listener added in this cycle closes the window
where one tab has already parked a record and the other has not noticed it, but
nothing on the client can serialize two creates that are genuinely concurrent.

Closing it properly needs per-(owner, night) uniqueness or idempotency inside
`create_night_out`, which is a migration against a function no finding in this
goal names — the same reason `0051` was removed above. It needs its own goal and
its own tier decision.

### And out of the round-3 cycle: an unwritable store loses the parked plan

Filed by Codex against `StartNightOutButton.tsx` and **not fixed**, because it
cannot be fixed at this layer. When `localStorage.setItem` throws — Safari
private mode at quota, a restricted webview — the parked record survives only in
a module-level variable, which dies with the JavaScript realm. Create succeeds,
the follow-up read fails, the user closes the tab, reopens the same night and
presses Start: a second plan.

Every client store available here has already been tried. sessionStorage dies
with the tab, localStorage is the store that just refused the write, and the
in-memory fallback dies with the realm. Recovering across a realm needs the
server to answer either "does this owner already have a plan for this night?" —
which no RPC exposes, and which is the *third* recorded product gap above — or
to make `create_night_out` idempotent per `(owner, night)` so a duplicate create
cannot happen at all.

That last option is the same fix the two items above want, and it is now named
by three separate reviewer findings across two rounds. It is the recommended
shape for the follow-up goal. It was deliberately NOT written here: it is a T0
migration, this worktree holds no staging credentials, and criterion 3's own
precedent is that a migration ships with a two-session staging repro. Shipping
an unapplied, unverified `create_night_out` replacement is exactly the state
`0051` was in when it was removed.

### Round 5: two cross-realm coordination gaps that stay open

Both filed by Codex against `StartNightOutButton.tsx`, both **not fixed**, and
both the same root cause as the two items above.

**The parked map is a non-atomic read-modify-write.** `readAll()` and
`writeAll()` are adjacent synchronous calls, so no caller holds a stale snapshot
across an await — but two tabs can still interleave between the two localStorage
syscalls, and the loser's write erases the winner's entry. `accountCache.ts`
solved its own version of this by construction (stamped entries, last-writer-wins
per key, an ack that only clears the write it acknowledges); there is no
equivalent construction here, because the thing being written IS the whole
per-account map. Closing it properly needs a real mutex — `navigator.locks` — or
the server.

**An account deleted in one tab can have its identifiers rewritten by another
tab's in-flight create.** The fix landed this round catches a record that was
PRESENT and is now ABSENT, which covers the common case (the owner opened that
plan elsewhere). It does not catch a create that had never parked anything when
the deletion ran: no diff of this key can distinguish that from an ordinary
concurrent write, and inventing a signal for it — a tombstone naming the deleted
user — would itself be the account residue the deletion exists to remove. The
leftover is one map entry the next prune removes and which the deleted account
can never act on.

**The pattern is the point.** Five review rounds have now produced findings
against this component in four of them, each one a consequence of the previous
round's fix. The mechanism — a durable, multi-account, cross-realm map
maintained without a lock — is carrying a coordination problem that does not
belong on the client. Every one of these findings ends at the same sentence:
*and then a second plan is created, because `create_night_out` has no
per-`(owner, night)` uniqueness*. That single server-side change collapses this
entire class. It is the recommended shape for the follow-up goal, and it should
be done before any further client patching.
