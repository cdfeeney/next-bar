# V9-06 — iPhone camera: prerequisites delivered, device acceptance INCOMPLETE

Goal g-7a7ac2a5, run nb-v9-overnight-20260908, on the V9-11 candidate (`7e17cea`). This goal cannot close in an
unattended run: its acceptance is a physical TestFlight iPhone. What follows is what was delivered, what was verified
in the browser, what needs a new iOS binary, and what is deliberately NOT done.

## 1. Native prerequisite — `NSCameraUsageDescription` (applied)

`ios/App/App/Info.plist` had no camera usage description. Apple's rule (Requesting authorization to capture and save
media): an app that accesses the camera without `NSCameraUsageDescription` is **terminated by the system** at the
first access — inside a WKWebView that is the moment the page calls `getUserMedia`. That is the most likely single
cause of "the camera does nothing / the app closes" on the TestFlight build; it is a concrete, required fix, and it is
not proven to be the sole cause because no device run has been observed with the key present.

Added: an honest, specific string ("…only when you tap to take a photo for a story or a moment. Nothing is captured
until you press the shutter, and the photo stays a draft until you approve it."). **Not added:** `NSMicrophoneUsageDescription`
(every `getUserMedia` call is `audio: false`; asking for a microphone we never use would be a false claim) and
`NSPhotoLibraryUsageDescription` (the library row is a web `<input type="file" accept="image/*">`; WKWebView serves it
through the system picker, which does not require the key — add it only if a native PHPhotoLibrary path ever appears).

**A plist change needs a new staging-targeted iOS binary.** Web deploys do not carry it. The attended device step is:
build via the TestFlight workflow with `CAP_SERVER_URL` pointing at staging, install, open Add to Story, and observe
the system camera prompt (first run) and the live preview.

## 2. Media-capture permission scope — own origin only (applied at the two layers this host can verify)

**The gap.** Capacitor 8.5.0's `WebViewDelegationHandler.swift:52-58` implements
`webView(_:requestMediaCapturePermissionFor:initiatedByFrame:type:decisionHandler:)` with an **unconditional
`.grant`**: whatever origin asks, from whatever frame, gets the camera without the delegate looking. Apple's guidance
is to decide per origin. So the two ways a foreign origin could reach `getUserMedia` inside the shell had to be closed
where this candidate CAN close them, and both are verified by the gates:

1. **Main-frame navigation** — `capacitor.config.ts` `allowNavigation` no longer allow-lists the canonical hosts
   alongside an override. Before, a staging-targeted binary (`CAP_SERVER_URL` = staging) could be navigated to
   `next-bar.com` and hand the camera to production's origin, which is exactly the "arbitrary origin" the goal
   forbids (round-1 Codex HIGH). Now: with an override, the ONLY allowed host is the override; without one, the
   canonical apex + www (one origin's two spellings). Anything else opens in Safari, outside the shell's grant.
2. **Embedded frames** — `next.config.js` sends `Permissions-Policy: camera=(self), microphone=()` on every route.
   A cross-origin iframe cannot even ask for the camera (the top document has to delegate it, and now never does),
   and the microphone is denied everywhere because this app never requests audio. Asserted by the e2e header test
   in `add-story.spec.ts` on `/`, `/friends`, `/map`.

**What remains native (defence in depth, needs a Mac).** With 1 and 2 in place the delegate's unconditional grant can
only be reached by the app's own origin. Tightening the delegate itself is still right, and the earlier sketch here
was wrong about how to install it (round-1 panel, both lanes): `CAPBridgeViewController` does not implement the
media-capture delegate method, its `loadView` creates the `WebViewDelegationHandler` and installs it as `uiDelegate`
before `capacitorDidLoad()` runs, and the handler's `bridge` setter is module-internal. The route that works:
subclass `CAPBridgeViewController` (set it as the storyboard's `customClass`), override `capacitorDidLoad()`, and
wrap `webView?.uiDelegate` in a forwarding `WKUIDelegate` that answers only `requestMediaCapturePermissionFor` —
`.grant` when `type == .camera`, `origin.protocol == "https"` and `origin.host` equals the configured server host,
`.deny` otherwise — and forwards every other selector to the original handler (`forwardingTarget(for:)` +
`responds(to:)`). Uncompiled Swift is not committed from a Windows host; this is the attended Mac/CI step, and the
iPhone acceptance includes it.

## 3. Web-side states — distinguishable, with accurate guidance (applied, tested)

`src/components/capture/useCamera.ts` keeps the two-way `status` (`denied` | `unavailable`) the stage renders on and
adds `reason`, set from the platform's error where it exposes one (`classifyCameraError`, pure, unit-tested):

| `reason` | From | Guidance (`cameraCopy.ts`) |
|---|---|---|
| `denied` | `NotAllowedError`, `SecurityError`, `PermissionDeniedError` | Settings › Privacy & Security › Camera › Next Bar on iPhone (stable across iOS 17/18); Safari aA › Website Settings; library |
| `no-api` | no `navigator.mediaDevices.getUserMedia` (insecure context / WebView without capture) | open in Safari or the app; library |
| `no-device` | `NotFoundError`, `DevicesNotFoundError`, `OverconstrainedError` | no lens faces this way; try the other lens; library |
| `busy` | `NotReadableError`, `TrackStartError`, `AbortError` | camera held by another app/tab or failed to start; try again; library |
| `ended` | live track `ended` (permission revoked mid-session, device claimed) | try again; library |
| `unknown` | anything else | generic unavailable; library |

Retry, library and cancel are unchanged; the stream is still stopped and the video element cleared on exit (the
effect cleanup already did this). The stage exposes `data-camera-status` and now `data-camera-reason` for tests.
The denied copy no longer says only "browser settings": inside the iPhone app the switch is in iOS Settings under the
app, which is where the owner will look.

## 4. Native vs web applicability

| Concern | Web (Safari / PWA) | iPhone app (WKWebView, remote origin) |
|---|---|---|
| Usage description | n/a | **Required** — missing = process terminated on first access (fixed, needs new binary) |
| Permission prompt | Safari's per-site prompt; remembered per site | WKWebView delegate decides; Capacitor grants unconditionally, reachable only by the app's own origin after §2 (navigation + Permissions-Policy); iOS still shows the system camera prompt once per app |
| Denied state | `NotAllowedError` → Settings guidance (Safari aA menu) | `NotAllowedError` → Settings › Privacy & Security › Camera › Next Bar |
| Busy / no device | `NotReadableError` / `NotFoundError` as mapped | same errors surface through WKWebView |
| Library fallback | `<input type=file>` → Files/Photos picker | system picker; no photo-library key needed |
| Audio | never requested | never requested; no microphone key on purpose |
