## 1. Native prerequisite — `NSCameraUsageDescription` (applied)

`ios/App/App/Info.plist` had no camera usage description. Apple's rule (Requesting authorization to capture and save
media): an app that accesses the camera without `NSCameraUsageDescription` is **terminated by the system** at the
first access — inside a WKWebView that is the moment the page calls `getUserMedia`. That is the most likely single
cause of "the camera does nothing / the app closes" on the TestFlight build; it is a concrete, required fix, and it is
not proven to be the sole cause because no device run has been observed with the key present.

Added: an honest, specific string ("…only when you tap to take a photo for a story or a moment. Nothing is captured
until you press the shutter, and the photo stays a draft until you approve it."). **Not added:** `NSMicrophoneUsageDescription`
(every `getUserMedia` call is `audio: false`; asking for a microphone we never use would be a false claim) and
`NSPhotoLibraryUsageDescription` (the library row is a web `<input type="file" accept="image/*">`; WKWebView serves it
through the system picker, which does not require the key — add it only if a native PHPhotoLibrary path ever appears).

**A plist change needs a new staging-targeted iOS binary.** Web deploys do not carry it. The attended device step is:
build via the TestFlight workflow with `CAP_SERVER_URL` pointing at staging, install, open Add to Story, and observe
the system camera prompt (first run) and the live preview.

## 2. Media-capture permission scope — GAP, not applied (needs a Mac to verify)

Capacitor 8.5.0's `WebViewDelegationHandler.swift:52-58` implements `webView(_:requestMediaCapturePermissionFor:
initiatedByFrame:type:decisionHandler:)` with an **unconditional `.grant`**. Any origin the WebView can navigate to
(`capacitor.config.ts` `allowNavigation`: the configured server host, `next-bar.com`, `www.next-bar.com`) would be
granted camera capture without a prompt. Apple's guidance is to decide per origin; the app's own origin should be
granted (or prompted once), everything else denied.

The fix is native: subclass `CAPBridgeViewController` (or the delegation handler) and override that delegate to
`.grant` only when `origin.protocol == "https"` and `origin.host` equals the configured server host, `.deny` otherwise:

```swift
// Proposed — NOT applied here (unverifiable without Xcode on this host)
override func webView(_ webView: WKWebView,
                      requestMediaCapturePermissionFor origin: WKSecurityOrigin,
                      initiatedByFrame frame: WKFrameInfo,
                      type: WKMediaCaptureType,
                      decisionHandler: @escaping (WKPermissionDecision) -> Void) {
    let own = bridge?.config.serverURL
    let isOwn = origin.protocol == "https" && own != nil && origin.host == own!.host
    decisionHandler(isOwn && type == .camera ? .grant : .deny)
}
```

Why it is not in this candidate: this worktree runs on Windows with no Xcode; uncompiled Swift cannot be typechecked,
and a syntax or API slip would fail the TestFlight build at exactly the attended step this goal is preparing. It is
recorded here for the person with a Mac (or the CI workflow) to apply and compile, and it is the second half of the
iPhone acceptance.

## 3. Web-side states — distinguishable, with accurate guidance (applied, tested)

`src/components/capture/useCamera.ts` keeps the two-way `status` (`denied` | `unavailable`) the stage renders on and
adds `reason`, set from the platform's error where it exposes one (`classifyCameraError`, pure, unit-tested):

| `reason` | From | Guidance (`cameraCopy.ts`) |
|---|---|---|
| `denied` | `NotAllowedError`, `SecurityError`, `PermissionDeniedError` | Settings › Next Bar › Camera on iPhone; Safari aA › Website Settings; library |
| `no-api` | no `navigator.mediaDevices.getUserMedia` (insecure context / WebView without capture) | open in Safari or the app; library |
| `no-device` | `NotFoundError`, `DevicesNotFoundError`, `OverconstrainedError` | no lens faces this way; try the other lens; library |
| `busy` | `NotReadableError`, `TrackStartError`, `AbortError` | camera held by another app/tab or failed to start; try again; library |
| `ended` | live track `ended` (permission revoked mid-session, device claimed) | try again; library |
| `unknown` | anything else | generic unavailable; library |

Retry, library and cancel are unchanged; the stream is still stopped and the video element cleared on exit (the
effect cleanup already did this). The stage exposes `data-camera-status` and now `data-camera-reason` for tests.
The denied copy no longer says only "browser settings": inside the iPhone app the switch is in iOS Settings under the
app, which is where the owner will look.

## 4. Native vs web applicability

| Concern | Web (Safari / PWA) | iPhone app (WKWebView, remote origin) |
|---|---|---|
| Usage description | n/a | **Required** — missing = process terminated on first access (fixed, needs new binary) |
| Permission prompt | Safari's per-site prompt; remembered per site | WKWebView delegate decides; Capacitor grants unconditionally today (§2 gap); iOS still shows the system camera prompt once per app |
| Denied state | `NotAllowedError` → Settings guidance (Safari aA menu) | `NotAllowedError` → Settings › Next Bar › Camera |
| Busy / no device | `NotReadableError` / `NotFoundError` as mapped | same errors surface through WKWebView |
| Library fallback | `<input type=file>` → Files/Photos picker | system picker; no photo-library key needed |
| Audio | never requested | never requested; no microphone key on purpose |
