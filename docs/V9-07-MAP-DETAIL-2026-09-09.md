# V9-07 — map venue name → shared photos & hours → top-right ✕ → the map exactly as it was

Goal g-26bce749, run nb-v9-overnight-20260908, on the V9-01 candidate (`cfeac0a`). Depends on foundation C, which made
the map's two ways of surfacing a venue (marker tap, map search) open ONE popup on the bar's own marker.

## What changed

- `src/components/BarMap.tsx` — the venue name in that one popup is now a button ("{name}, photos and hours") that
  opens `BarLightbox` for exactly that bar; `BarMap` holds the open venue and renders the lightbox through a portal to
  `document.body`. Two reasons for the portal rather than an inline overlay: the popup lives inside a transformed
  Leaflet pane, which would re-anchor a `position: fixed` overlay to the pane; and the `/map` surface is a fixed
  `<main>` that stacks BELOW the bottom nav, so an overlay inside it would render under the tabs. Directions origin is
  the map's `userCoords` when known. The name focuses itself before opening: WebKit does not focus a button on
  tap, and the lightbox returns focus to whatever was active when it opened, so on iOS a tapped name would otherwise
  hand focus back to the page (found by the marker journey on iPhone 13). Nothing else on the map changes: no media prefetch across pins (the lightbox
  fetches details for the one open bar, as it always has), no HTML interpolation (React text nodes), no rehosted
  photos, no external map handoff from the popup.
- `src/components/BarLightbox.tsx` — the header row, whose right-hand end is the ✕, now clears the top safe area
  (`pt-[max(1.5rem,env(safe-area-inset-top))]`). This is the shared detail surface, so result cards get it too.
- `src/components/BarLightbox.tsx` — Escape is now handled in the **capture** phase and stopped there. Found by the
  marker journey on Pixel 7: Leaflet's keyboard handler listens on `document` and closes the open venue popup on
  Escape (`closeOnEscapeKey`), so pressing Escape in the dialog closed the dialog AND the popup underneath — taking
  the map's selection, and the element the dialog returns focus to, with it. A modal owns Escape while open; this
  applies to result-card lightboxes too, where nothing underneath listened, so behaviour there is unchanged.
- `ResultCard.tsx` and `src/app/map/page.tsx` — no change needed: the card already mounts the same lightbox, and the
  page's search → `focusBarId` → popup path lands on the same popup content.

**Colour.** The owner asked for a visibly light-blue name. The Leaflet popup card is white (no override in
`globals.css`), and the pale blues fail 4.5:1 there, so the control is sky-600 (`#0284c7`) with an underline — a
blue that reads as "opens something" and passes AA. If the popup is ever restyled dark, lighten it then.

## Why closing "restores" the map without restoring anything

The lightbox is an overlay; the `MapContainer` never unmounts and no prop it reads changes when the overlay opens or
closes. Center, zoom, the open popup and the page's filters are therefore untouched by construction, and `BarLightbox`
already returns focus to the element that opened it (the popup name). The e2e journeys assert this on the map's
published center and zoom and on the popup's screen rectangle before and after, not on visibility alone.

**Readiness, not sleeps.** `BarMap` now publishes `data-map-moving` (between Leaflet's `movestart` and `moveend`) and
`data-map-center` / `data-map-zoom` (on every settle) on the map container. Leaflet's `flyTo` repositions layers by
pixel origin rather than by the pane transform, so nothing else in the DOM says whether the map is still in flight —
and headless WebKit stalls animation frames long enough that "two identical reads 200 ms apart" passed mid-flight on
the first run (the popup rect then moved once the fly-to finished; no scroll container had moved). The journeys wait
on the map's own `moveend` instead.
