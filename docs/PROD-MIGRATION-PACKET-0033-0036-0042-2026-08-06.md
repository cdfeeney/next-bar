## 4. Checksums and the normalization contract

### 4.1 The contract

`src/lib/migrationPlan.ts:54-57`:

```js
const normalised = sql.replace(/\r\n/g, '\n').replace(/\s+$/, '');
return createHash('sha256').update(normalised, 'utf8').digest('hex');
```

Two normalizations, both load-bearing on this project:

- **CRLF → LF.** The repo is developed on Windows with `core.autocrlf` active,
  so the same migration is CRLF on one checkout and LF on another. Hashing raw
  bytes would report drift on every checkout and make the drift guard useless
  noise. Every file in this worktree is **CRLF on disk** (verified), and every
  checksum below is computed after collapsing that.
- **Trailing whitespace stripped** (`/\s+$/`, end-of-string only, not
  per-line). A trailing-newline difference is not a schema change.

A BOM is **not** normalized away. A UTF-8 BOM changes the hash — this is how
the earlier PowerShell `Set-Content` BOM incident was caught during the
0033–0036 packet. Never re-materialize these files with a shell redirect; use
`git checkout`.

### 4.2 Values

0033–0036 values are **preserved from the approved packet, not recomputed into
it** — the replication was validated against them as controls, 4/4 matching,
which is what makes the fifth value trustworthy.

## 6. Cross-migration behavior

### 6.1 Ordering

The runner applies in lexical filename order (`readdirSync(...).sort()`), so
the window is 0033 → 0034 → 0035 → 0036 → 0042. 0042 is written to apply
**directly after 0036** — its own header states this (lines 8–12).

### 6.2 Locking — 0034 is the disruptive one

`0034_revoke_first_grants.sql` issues `revoke all` / `grant` across the four
core user tables (line 42 onward). In PostgreSQL, `REVOKE`/`GRANT` on a table
takes **ACCESS EXCLUSIVE**: concurrent queries against those tables do not
error, they **queue and hang** for the duration. This was DeepSeek's finding in
the approved packet's round 3 and is carried forward unchanged.

Consequence for the window: **run it in a low-traffic period**, and expect the
live client to stall rather than fail during 0034. 0042 by contrast creates a
brand-new table — nothing existing contends for it.

**Mitigation — already specified and reviewed in the approved packet, lines
166–170 and 288–292.** Carry a short `lock_timeout` so 0034 fails fast and
rolls back instead of queueing behind a long transaction. The runner sets none
and accepts no flag for it, so it must be carried on the connection:

```
$env:PGOPTIONS = '-c lock_timeout=5s'
```

or as a `DATABASE_URL` parameter — `?options=-c%20lock_timeout%3D5s` when the
URL has no query string, **`&options=…` when it already does** (Codex,
re-verdict). **Verify with `show lock_timeout;` on that exact connection
string before applying** — an unverified assumption here silently buys nothing.
Pair it with a pre-flight `pg_stat_activity` check for long-running
transactions on the four tables 0034 touches.

### 6.3 Old-client behavior during and after the window

- **During:** the deployed old client (Production's current `6ec5e5d`) queues
  on 0034's locks. It does not receive errors; it waits.
- **After:** 0034 re-grants every privilege the deployed client actually uses
  (verified in the approved packet's round-2 Codex pass). 0042 adds a table the
  old client never queries — it is inert for `6ec5e5d`, so the schema can land
  before the code does.
- **Stale-write semantics:** the LWW trigger's `return null` on a `<=` client
  clock is a **silent no-op**, not an error. Only a client performing read-back
  confirmation detects it. The old client never writes this table, so this
  matters only after the new code deploys.

### 6.4 0036's ledger privilege change and why the verifier uses `DATABASE_URL`

0036 enables RLS on `public.schema_migrations` and revokes all privileges from
`public, anon, authenticated` (lines 38–40). It closes the P1 finding — today
Production's ledger is **anon-readable**, which is how the 2026-08-05
reconciliation obtained it.

This is precisely why the pre-apply verifier reads through the privileged
`DATABASE_URL`: an anon-key ledger check would stop working the moment the
migration it is verifying succeeds. The migration owner is exempt from
privilege checks and RLS, so the runner and verifier keep working afterward.

### 6.5 0042 has no dependency on the absent 0037–0041

Stated in the migration itself, lines 8–12:

> `0037–0041 are deliberately absent from the Beta 1 RC. This migration is 0042
> because those numbers already belong to census/social work on other branches;
> migration identity must never be reused for different SQL. 0042 has NO
> dependency on any of 0037–0041 — it applies cleanly directly after 0036, and

### 7.2 Why the runner ignores them

`planMigrations` builds `recorded` as a **name-keyed Map** of ledger rows
(`src/lib/migrationPlan.ts:558`) and then iterates **files only**
(`:564`). A ledger row with no corresponding file is never visited: it cannot
enter `apply`, `skip` or `drift`. Orphan ledger rows are therefore inert —
they neither trigger drift nor cause a re-run. This is the same property that
lets the 0033–0036 branch plan correctly without carrying files 0020–0032.

not an oversight: their files are not in the candidate, so there is nothing to
apply, and inventing them here would be exactly the retroactive gap-filling
0042's header forbids.

### 7.4 Schema divergence is not runtime dependency

After this window, Production's schema will differ from Staging's by whatever
0037 and 0041 created. That is **schema divergence**. It becomes a **runtime
dependency** only if the shipping code reads those objects — and it does not:

```
grep -rl "census_runs|census_evidence|'census'|\"census\"" src/ --include=*.ts --include=*.tsx
  → no matches
```

The candidate's web runtime contains **zero references** to census objects or
to `source = 'census'`. 0041 widens an allowed value the candidate never

**Residual, stated honestly:** the grep covers `src/` — the application

## 8. Failure and rollback

### 8.1 Fail closed before anything runs

The §3 verifier exits non-zero unless the plan matches `--expect` **exactly**
in count and order with `drift 0`
(`scripts/release/verify-migration-plan.mts:70-75`). An unexpected extra
migration breaks the count; a reordered one breaks the index match; any
checksum drift additionally forces `apply: []` upstream
(`src/lib/migrationPlan.ts:580`). **A non-zero exit ends the window.**

The runner independently re-plans and re-checks drift at apply time
(`scripts/apply-migrations.ts:355-378`), so the verifier is a matching gate,
not the only guard.

### 8.2 Transaction boundaries

Each migration and its ledger row commit **together**, in one transaction per
file (`scripts/apply-migrations.ts:487-503`): `begin` → migration body →
`insert into public.schema_migrations` → `commit`, with `rollback` on error and
an immediate stop. A failure therefore leaves:

- the failed migration **fully rolled back**, and
- the ledger holding a **truthful, resumable prefix** — every migration that
  did apply is recorded, and the failed one is not.

Recovery from a partial apply is to **fix forward and re-run the runner**,
which will resume at the first unapplied file. **Do not delete ledger rows for
migrations that genuinely applied.**

### 8.3 Deployment gate

**Do not begin the application deployment unless all five migrations are
confirmed applied** (ledger 38 rows, §9.1). The new code requires
`account_content_state`; deploying it against a schema missing 0042 puts the
account-persistence feature in front of users with no table behind it.

Schema-before-code is safe here because 0042 is inert for the old client (§6.3).

### 8.4 Code rollback vs SQL rollback — they are not the same lever

- **Code rollback is the primary lever.** Re-point the Vercel deployment to
  the previous Production build. This is fast, reversible, and sufficient for
  any application-level defect, because the migrated schema remains compatible
  with the old client (§6.3).
- **SQL rollback is a last resort under separate review.** Each migration's
  rollback statements live in trailing comments and must be executed
  deliberately, in reverse order, together with the matching ledger `DELETE` —
  otherwise a later run silently skips a reverted migration
  (`planMigrations` treats a present ledger row + matching file as `skip`).

### 8.5 0042's drop block must never run automatically

`0042` lines 132–137 are **comments**. They drop both triggers, both functions,
and the table — destroying every user's synced lists and night history.

**They must never be executed automatically, never as part of a rollback
script, and never as a reflex during an incident.** Restoring the pre-window
state does not require dropping this table: the table is inert to the old
client, so a **code rollback alone** restores prior behavior while preserving
the data. Dropping it is a data-loss event that requires its own reviewed
recovery plan and an explicit operator decision.

### 8.6 Roll-forward decision points

| Point | Signal | Decision |
|---|---|---|
| Pre-apply | verifier non-zero | **Abort.** Do not apply. No state changed. |
| After 0033/0034/0035 | migration error | Runner already rolled back that file. **Roll forward** (fix + re-run) — do not hand-revert. |
| After 0036 | ledger no longer anon-readable | Expected. Verify (§9.5), continue. |
| After 0042 | any §9.4 check fails | **Stop before deploying code.** Schema is safe for the old client; investigate with no user impact. |
| Post-deploy | app-level defect | **Code rollback**, not SQL rollback (§8.4). |
| Any point | data-loss suspicion | Stop; do **not** touch §8.5; escalate to operator. |

### 9.2 Privileges and RLS

```sql
select relname, relrowsecurity
  from pg_class
 where relname in ('account_content_state','schema_migrations','profiles');

select grantee, privilege_type
  from information_schema.role_table_grants
 where table_name = 'account_content_state'
 order by grantee, privilege_type;
```

RLS must be **true** on both new/protected tables.

**Do not expect `authenticated` to be the only grantee.** Three other
principals legitimately appear and are **not** failures:

- the **table owner** (the migration role), whose privileges are implicit and
  always listed;
- **`service_role`**, which 0042 deliberately does not name in its revoke
  (line 73 revokes from `public, anon, authenticated` only) — the same
  revoke-first convention 0034 documents, keeping the backend role intact;
- any role Supabase default privileges grant that is neither `PUBLIC` nor
  `anon`.

**Fail on exactly this:** any privilege held by **`PUBLIC`** or **`anon`** on
`public.account_content_state`. Either one means account content is reachable
by an unauthenticated caller and the window must abort.

Then confirm `authenticated` holds only the intended owner-scoped access —
privileges exactly `SELECT, INSERT, UPDATE, DELETE` (no `TRUNCATE`,
`REFERENCES` or `TRIGGER`), and scoped by the four policies of §9.4 rather
than by the grant itself. The grant is table-wide by design; **RLS is what
makes it owner-scoped**, which is why RLS being `true` above is the
load-bearing half of this check, not the grant list.

### 9.3 0033–0036 objects

Per the approved packet's §5: `vibe_profiles` present with its columns,
trigger and function (not existence-only — `CREATE TABLE IF NOT EXISTS` would
pass a malformed pre-existing table); 0034's re-grants present on all four core
tables including the column-scoped `profiles` grant; 0035's date-bound check on
`share_night`.

### 9.4 `account_content_state` constraints, policies and both triggers

```sql
select conname, contype from pg_constraint
 where conrelid = 'public.account_content_state'::regclass
 order by conname;

select policyname, cmd from pg_policies
 where tablename = 'account_content_state';
-- expect 4 owner-only policies: select, insert, update, delete

select tgname from pg_trigger
 where tgrelid = 'public.account_content_state'::regclass
   and not tgisinternal;
-- expect BOTH: account_content_state_clock, account_content_state_lww
```

**This is a presence check, not a row count.** Assert that each required
**named** constraint is present:

| Constraint | `contype` |
|---|---|
| `account_content_state_pkey` | `p` |
| `account_content_state_key_check` | `c` |
| `account_content_state_payload_object` | `c` |
| `account_content_state_payload_size` | `c` |

**Additional rows are expected and must not abort the window.** At minimum the
**foreign key** on `user_id → auth.users(id) on delete cascade` (0042 line 24,
`contype = 'f'`, auto-named `account_content_state_user_id_fkey`) will always
appear. On **PostgreSQL 17+**, `NOT NULL` constraints are also catalogued in
`pg_constraint` (`contype = 'n'`), adding up to five further rows. The row
count is therefore version-dependent and must never be the criterion.

**Abort condition:** any of the four named constraints above **absent**, or
the `user_id` foreign key absent. An unrecognised *extra* constraint is a
note, not an abort — record it and continue.

**Both triggers must be present.** The clock trigger missing means bogus
client clocks enter the LWW ordering permanently; the LWW trigger missing
means stale writes overwrite newer ones with no error.

### 9.5 Post-migration anon-ledger denial

The P1 closure check. From an **anonymous** browser-key context (not the
privileged connection), attempt to read `public.schema_migrations`. Expect a
denial — **not** a `200` with rows. Before this window that read succeeds;
after 0036 it must not.

### 9.6 Abort conditions

Abort the window and stop before deploying if **any** of these hold:

- the verifier exits non-zero;
- the ledger is not **38 rows**, or any of the five names is absent;
- RLS is `false` on `account_content_state` or `schema_migrations`;
- **`PUBLIC` or `anon` holds any privilege** on `account_content_state` (§9.2);
- fewer than the **4 named policies**, or any of the **4 named constraints**
  or the **`user_id` foreign key** is absent (§9.4);
- **either** trigger is absent;
- anon can still read the ledger (§9.5);
- any migration reports an error the runner did not roll back.

**Not abort conditions:** extra grantees other than `PUBLIC`/`anon` (owner,
`service_role`); extra `pg_constraint` rows, including PostgreSQL 17+ `NOT
NULL` entries. Record them and continue.
