# Supabase RLS audit — 2026-07-30

Audit only. No migration was applied, no database mutated. Every claim is derived
from `supabase/migrations/*.sql` (34 files, `0000`–`0033`).

**Headline: the RLS posture is sound.** All 19 tables have RLS enabled, all 29
`security definer` functions pin `search_path`, and only two policies are not
`auth.uid()`-scoped — both deliberately public. The findings below are hardening
gaps and one inconsistency, not holes.

> **Scope limit, stated up front:** this describes what the *migrations declare*.
> It cannot prove what production *enforces* — a policy changed by hand in the
> Supabase dashboard would be invisible here. See §6.

## 1. Counts, re-derived

**Counting rule — the correction that reshaped this audit.** A first pass counted
statements across migration *files*. That is the wrong unit: migrations `drop`
and `create or replace`, so the file count and the **final schema** differ. Every
number below is the state *after applying `0000`–`0032` in order*, with `0033`
called out separately because it is unapplied.

| Fact | Statements in files | **Final schema** | Note |
|---|---|---|---|
| Migrations | 34 (`0000`–`0033`) | — | `0033_vibe_profiles` authored, **NOT applied** |
| Tables created | 19 | 19 | |
| Tables with RLS enabled | — | **19 / 19** | no user-data table is unprotected |
| `create policy` statements | 27 | **25** | `0014` drops `bar_rsvps_delete_own`; `0021` replaces one |
| Tables carrying policies | 13 | **12** | `bar_rsvps` loses its only policy |
| Tables with RLS and **zero** policies | — | **7** | deny-all — §3 |
| `security definer` functions | 31 definitions | **29** | `0008` replaces `follow_user`; `0021` drops `pending_change_count(uuid)` |
| …browser-callable as RPCs | — | **28** | `handle_new_user` is trigger-only |
| …with `search_path` pinned | — | **29 / 29** | none unpinned |

### Three derivation errors, recorded because each nearly became a finding

0. **The whole enumeration was initially statement-based, not schema-based** —
   see the counting rule above. That single error inflated the policy count
   (27 → 25), the table-with-policies count (13 → 12), and the function count
   (31 → 29), and it put `bar_rsvps` in the wrong section. Review caught it. Any
   regeneration must reason about the applied result, not the file contents.
1. **`ratings` appeared to have no RLS.** `0001:76` reads
   `alter table public.ratings  enable row level security;` — with **two spaces**.
   A whitespace-exact grep missed it and would have produced a CRITICAL false
   positive on the app's core user table.
2. **`bars` appeared to have no policy.** Its policy name is a bare identifier
   (`create policy bars_select_all …`), not quoted, so a regex requiring quotes
   skipped it — which would have claimed the public catalog was unreadable while
   the app demonstrably reads it.

Items 1 and 2 were caught by sanity-checking a surprising result against the app's actual
behaviour. In a security audit a false "no protection" claim is as damaging as a
missed hole, so the enumeration here uses patterns tolerant of both quoting
styles and irregular whitespace.

## 3. RLS enabled with zero policies — deny-all, and that is the point

Seven tables have RLS on and no policy, so PostgREST denies `anon` and
`authenticated` outright. Each is reachable only through a `security definer`
function that enforces its own rules:

| Table | Reached via |
|---|---|
| `analytics_events` | `bump_analytics_event` — note this is security-**invoker**, not definer; it works because `0018` grants execute to `service_role` only, which also bypasses RLS |
| `shared_nights` | `share_night` / `unshare_night` / `get_shared_night` |
| `follow_attempts` | internal rate-limit counter, written by follow RPCs |
| `handle_claim_attempts` | internal, written by `claim_handle` |
| `handle_search_attempts` | internal, written by `search_handles` |
| `photo_permissions` | **no RPC at all** — service-role only; the A7 inventory confirmed no app code touches it |
| `bar_rsvps` | `rsvp_bar` / `unrsvp_bar` / `get_circle_rsvps`; `0014` deliberately closed the direct-delete window opened by `0012` |

This is the correct pattern for RPC-mediated tables: the client cannot touch the
table directly, and the function is the only door. **Deny-all here is a feature,
not a missing policy** — worth stating plainly, because a naive audit flags all seven as gaps.

Two of the seven are **not** reached via a security-definer RPC, and an earlier
draft claimed all of them were: `analytics_events` goes through a
security-**invoker** function that works only because execute is granted to
`service_role`, and `photo_permissions` has no RPC at all. Their client denial is
sound; the architectural explanation was wrong.

## 4. Findings

### F1 — MEDIUM · `search_path = public` is pinned everywhere, but `''` is stricter
All 29 surviving `security definer` functions set `search_path = public`. That is the
important half — an unpinned `security definer` function is a privilege-escalation
vector, and there are none here.

The stricter form is `set search_path = ''` with fully-qualified object names,
which removes any dependence on what `public` contains. The codebase already
knows this: `0033_vibe_profiles.sql`'s trigger guard uses `set search_path = ''`.
So the project uses two standards, and the newer, stricter one is applied only in
the newest migration.

*Risk today:* low. On modern Postgres (15+), `CREATE` on `public` is no longer
granted to `PUBLIC` by default, so a non-superuser cannot plant a shadowing
object. It matters if that default is ever relaxed, or on an older instance.

*Fix:* prefer `set search_path = ''` for new `security definer` functions; treat
back-porting the existing 29 as optional hardening, not urgent.

### F2 — MEDIUM · The RPC surface, not the table surface, is where authorization actually lives
**28** security-definer functions are callable directly from the browser via
PostgREST. Because they run as their definer, **RLS does not constrain them** —
each one's own body is the entire access-control boundary for the rows it
touches.

That is a lot of authorization logic living outside the policy system, and this
audit's per-table matrix does not capture it. Spot-reading confirms the pattern
is sound where checked — `search_handles` (`0006`) returns only
`handle, display_name`, filters `is_private = false`, and caps at 500 searches/day;
`get_public_ratings` (`0015`) is the deliberate public-share path — but "spot-read
and it looked right" is not an audit.

*Recommendation:* a follow-up pass that reviews all 28 callable function bodies as
authorization code, asking per function: does it derive identity from
`auth.uid()` rather than a parameter, does it return more than it claims, and is
it rate-capped where it enumerates. That is a real piece of work and is the
highest-value security item remaining after this audit.

### F3 — MEDIUM · Three tables skip the project's own revoke-first pattern
`0019:80` states the house rule: "the house pattern is per-object revoke-first".
Twelve migration files follow it. **Four** core user tables do not:

| Table | revoke | grant |
|---|---|---|
| `ratings` | `revoke all … from anon` only | relies on default for `authenticated` |
| `pairwise_comparisons` | **none** | **none** — relies entirely on defaults |
| `vibe_profiles` | **none** | **none** — relies entirely on defaults |
| `profiles` | `revoke update` only (`0006`) | select/insert/delete rely on defaults |

`profiles` was missed in the first draft — `0006` revokes only UPDATE and
re-grants two columns, never revoke-firsting the rest. With RLS on and
owner-only policies none of the four is **exposed today**: `anon` has no
`auth.uid()`, so it matches no row. The gap is defence-in-depth — a
revoke-first table survives RLS being accidentally disabled, a defaults-reliant
table does not.

**`vibe_profiles` is mine**, authored earlier in this same work queue. I matched
`0001`'s policy style but not `0019`'s grant style, and did not notice the
codebase had two conventions until this audit. Recording rather than quietly
fixing, since the migration is unapplied and the fix belongs in a reviewed change.

*Fix:* add `revoke all on table public.<t> from public, anon, authenticated;`
followed by the minimal explicit grants, matching `0019`.

### F-good — worth copying, not fixing
`grant update (display_name, is_private) on table public.profiles to authenticated`
(`0006:83`) is **column-scoped**. Even a policy bug could not let a user rewrite
`handle` or `id` through PostgREST. This is stronger than RLS alone and is the
pattern other update paths should follow.

## 5. What I did *not* find

Stated explicitly, because an audit that reports only problems is hard to trust:

- **No table with RLS disabled.** All 19 enable it.
- **No `security definer` function without a pinned `search_path`.** All 31 pin it.
- **No policy granting broad access to user data.** The only two non-owner
  predicates are the public catalog and approved photos.
- **No grant that defeats a policy.** Every `anon`/`authenticated` table grant
  pairs with a policy that scopes it; there is no `grant all`.
- ~~No policy made unreachable by a revoke.~~ **This claim was wrong** and review
  caught it. `0007:72` revokes insert/update/delete on `follows` while its insert
  and delete policies remain — see F4. `0014` both revokes delete on `bar_rsvps`
  **and** drops its policy, which is the tidier version of the same move.

## 6. UNVERIFIED — operator-only

1. **Live database state.** This audit reads migrations. A policy added, altered,
   or dropped in the Supabase dashboard would not appear here. Confirming
   requires querying `pg_policies` against production.
2. **Whether `0033_vibe_profiles` has been applied.** It is authored and, as of
   this audit, unapplied — the `schema_migrations` ledger's last entry is `0032`.
3. **Postgres major version**, which decides whether F1's `public`-schema
   `CREATE` default matters.

### F4 — LOW · `follows` retains two policies its grants make unreachable
`0007:69-73` revokes `insert`/`update`/`delete` on `public.follows` from client
roles and grants only `select`; the insert and delete **policies** created
alongside them remain. Without the table privilege the policies can never be
evaluated by a client — writes go through `follow_user` / `unfollow_user`.

The comment at `0007:69-71` shows this is deliberate: the policies are kept as
"defense-in-depth should a blanket grant ever return". That is defensible, and
`0014` shows the alternative house style (revoke *and* drop the policy). Flagged
only because an audit that says "policies define access" is misleading here:
these two do not, and a reader comparing the two migrations will find two
different conventions for the same situation.

### F5 — MEDIUM · A column-scoped grant locks users out of their own public-share flag
`0006:83` grants `update (display_name, is_private)` on `profiles`.
`0015:37` later adds `shares_list_publicly boolean not null default false` and
`0015:74` makes `get_public_ratings` return rows only
`where p.shares_list_publicly = true`.

Nothing ever extends the grant to that column, and no RPC sets it. So an
authenticated owner running `update profiles set shares_list_publicly = true`
gets a column-permission error, and the public-shared-list feature can only be
switched on by a privileged role. The opt-in is unreachable by the people it is
for.

This is the flip side of the very pattern §4's *F-good* praises: column-scoped
grants are excellent, but they must be revisited whenever a user-settable column
is added. An audit that only praised the pattern would have missed this — review
caught it.

*Fix:* either extend the grant to `shares_list_publicly`, or add a small
`security definer` RPC that toggles it after checking `auth.uid()`.
